# 리뷰 뒤 실행할 기계적 검증

지금은 테스트 소스 작성과 정적 검토만 한다. 실행은 ChatGPT 전체 브랜치 리뷰 뒤다. 폐기된 상태 필드가 있는지 없는지보다 실제 상태·출력·저장의 결과를 검증한다. 다음의 서로 다른 위험에 필요한 작은 사례로 묶고 표현 변형마다 같은 검사를 늘리지 않는다.

1. **시작/진행/복원:** NEW 첫 질문 저장, turn 새 답만 전달, 한 메시지씩 누적, 답 없는 질문 재개. cache miss 시 입력 포함 full RESTORE 후 같은 delta가 한 번만 처리됨. RESTORE/기존 제안 표시 생성0회.
2. **중복/실패/timeout:** 같은 키 동일 본문 재전달, 키 재사용 다른 본문 충돌, 다른 턴 같은 답변 허용. 모델 실패에도 사용자 답변 보존, 실패 job 동일 입력 retry, 만료 job 복구, 동시 답변 차단, 늦은 결과 차단.
3. **제안/설명/정정:** 실제 USER 인용과 AI 예시 화자 구별. EXPLAIN_PROPOSAL 후 proposalId 유지·새 session revision 승인 허용. 실질 정정/변화 철회/처리 실패 후 옛 proposal 승인 불가. 새로운 AFTER+옛 라벨 혼합 저장 불가.
4. **최종 저장:** 제안 승인·모든 유형 거부·중복 confirm·stale confirm. 실제 보여 준 BEFORE/AFTER와 reviews·수치·COMPLETED의 원자성. 수락 유형이 없어도 AFTER 확인 허용. 수치 범위와 같은 초기 생각 대상 유지.
5. **중단/취소:** 나중에 이어하기 OPEN·제안 복원, cancel CANCELLED·문답 보존·재개 불가, 진행 중 cancel 뒤 성공 응답 저장 금지, 자연어 control이 cancel 호출하지 않음. 기존 safety stop 별도 상태.
6. **구형 데이터와 소비자:** 기존 question_answers/구형 결과/빈 필드 읽기, raw 유지·resultFormatVersion 분기, 새 상세/PDF/보고서/검색에 일관된 결과. 미승인/취소 결과 제외, 임베딩 실패가 결과 승인까지 롤백하지 않음.
7. **세 앱과 공용 경계:** API request/SessionView 타입·상태·헤더·인증/소유권·CORS 일치. 기록 생성/조회/정렬/이어하기 목록·기존 임베딩 retry가 개편 후 깨지지 않음. 실제 코드 리뷰에서 발견한 다른 구체적 영향이 있으면 그 관계의 사례만 추가.
8. **provider 경계:** 일반2·완료3·Writer 순수 형식복구 포함3, moderation1별도, SDKretry0. 최종 검토 예약·출력 cap·입력48k/196608bytes를 실제 직렬화 요청에 적용. 원문을 잘라 맞추지 않음. 무효 후보를 성공/no-clear로 바꾸지 않음.

동일 계약을 fake 출력으로 주입한 결과는 서버 기계적 테스트다. CBT 질문/AFTER 의미의 실제 모델 통과와 구분한다. 테스트 목적으로 운영 DB에 접속하거나 사용자의 기존 데이터를 초기화하지 않는다. 테스트 환경이 준비되지 않았다면 정확한 환경 의존을 보고하고 그 경로를 통과라고 쓰지 않는다.
