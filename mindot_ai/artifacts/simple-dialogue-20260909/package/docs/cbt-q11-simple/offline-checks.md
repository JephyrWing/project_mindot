# 오프라인 검증 계약

목적은 **구조를 단순화한 제품이 공개 API·메모리·실제 도구 연결을 유지하는지** 확인하는 것이다. 올바른 모델 응답을 주입하는 검사는 실제 모델의 질문 품질 증거로 세지 않는다. 질문 품질은 `canary-plan.json`의 실제 연속 대화에서 확인한다. 새로운 테스트 개수 목표나 안전 예외 유형 할당량을 만들지 않는다.

## 확인할 계약

아래 행마다 기존 검사가 충분하면 재사용한다. 검사 이름과 실제 증거를 매핑하되 행마다 새 테스트 파일이나 여러 중복 테스트를 만들 필요는 없다.

| 확인 대상 | 필요한 실행·비교 | 통과 의미 |
| --- | --- | --- |
| 공개 API와 클라이언트 연결 | 기존 OpenAPI/DTO를 기준으로 START, CONTINUE, CONFIRM_REQUIRED, SAFETY_STOP 응답을 실제 facade까지 통과시킨다. back/front는 읽기 전용으로 nullable 결과·확인·취소 처리만 확인한다. | 공개 URL·필드·enum 불변. 미판정·중단 안내는 CONTINUE 제어 응답이며 assessmentType/outcomeDraft는 null. AI가 DB 완료·취소 성공을 주장하지 않는다. 클라이언트 변경이 필요하면 AI에서 가능하다고 위장하지 않고 정확한 별도 제안으로 남긴다. |
| 실제 Agent 도구 실행 | 실제 provider SDK resource 경계의 fake로 tool call을 돌려 SELECT → 실제 Writer callable 및 SELECT → 실제 Assessor callable → 동일 Agent 검토를 각각 실행한다. | 실제 tool_call_id/ToolMessage가 연결되고 가짜 성공 기록이 없다. 일반 질문 2회, 평가 3회, 템플릿 제어는 최대 1회, 필요 없는 보정/재검토 호출이 추가되지 않는다. |
| 질문 출력의 단순화 | 같은 의미의 유효 문장에 자연스러운 종결·문장부호·줄바꿈 변형을 적용하고 실제 공개 응답 생성까지 확인한다. | 공개 500자 등 전달에 필요한 제약을 유지한다. 요?/까?·ASCII 물음표 개수·줄바꿈·고정 예문 접두어·내부 필드별 임의 길이 때문에 유효 질문이 실패하지 않는다. 질문 하나·맥락 적절성은 정규식이 증명한 것으로 기록하지 않는다. |
| coverage와 완료의 분리 | 영역별 증거를 모두 만들지 않은 현재 대화로 근거 있는 평가 초안을 실행한다. 별도로 아직 판단할 자료가 없는 결과와 사용자 중단을 실행한다. | 네 칸 채우기가 전제조건이 아니다. 미제공 자료를 만들지 않으며, 근거 있는 no-clear·판단 불가·일반 중단이 구분된다. acknowledgement 인용은 없으면 두 필드 모두 null이고, 초안의 정리 제안을 사용자가 이미 동의한 내용으로 쓰지 않는다. |
| 새 답변과 혼합 도움 요청 | 여러 실제 USER 원문 중 마지막에만 실질 답변+설명/예시 요청을 넣고 실제 선택/도구/commit을 통과시킨다. | 원문·내용이 보존되고 요청을 다른 답변 출처로 옮기지 않는다. 응답 후 요청 이행은 한 번만 기록되며 다음 턴에 재생하지 않는다. 슬롯별 리뷰/contribution 출력 수는 검사하지 않는다. |
| 정정·부분 철회·복권 | 두 절로 된 과거 답변에서 한 절을 정정·철회한 뒤 그 절만 명시적으로 복권하는 이력을 재생한다. | 나머지 유효 절은 남고 철회 구간과 그 파생 판정은 유효 근거에서 빠진다. 복권 후 중복 근거가 생기지 않고 원문 복원만으로 과거 요청/종결 상태를 임의 부활시키지 않는다. |
| 원래 자동사고의 효력 | 원래 자동사고 전체 철회와 일부 구간 철회를 각각 기존 계약에 맞게 재생한다. | 철회한 원래 생각으로 완료 평가하지 않는다. 대화 속 새 생각을 Spring의 원래 기록으로 몰래 대체하지 않는다. 필요한 기록 수정 안내는 기존 API/UI 범위에서 제공한다. |
| 닫힌 질문·요청 변경 | 명시적 없음·SKIP·반복 항의로 닫힌 목표, 설명 이행, 요청 취소/대상 변경을 실제 다음 턴까지 확인한다. | 자동으로 같은 질문을 다시 묻거나 이행/취소된 요청을 되살리지 않는다. 사용자가 명시적으로 다시 살펴보자고 할 때만 관련 목표를 재개한다. 불명확한 요청 대상을 서버가 의미 추측으로 확정하지 않는다. |
| 사실 확인 질문의 연속성 | Assessor의 실제 보충 질문 후보를 수락한 상태에서 설명 요청 → 실제 답변/생략 → 답변 또는 생략 철회를 재생한다. | 설명 요청을 보충 답변으로 세지 않는다. 답변 효력과 질문 사용 이력이 유지된다. 철회 뒤 필요한 대기는 완료나 새 보충 질문으로 위장되지 않는다. 같은 의미의 gap 질문 예산을 복원/재개 때 초기화하지 않는다. |
| 안전·중단·재개 | 명확한 현재 긴급 위험, 기존에 해소된 사건의 명시적 재개, 일반 중단 이후 사용자의 명시적 대화 재개를 기존 fixture로 확인한다. | 현재 위험 대응, 사건 이력·확인 사용량, 중단 의사를 잃지 않는다. 인용/과거 발화를 현재 사용자 위험이나 CBT 근거로 승격하지 않는다. 새로운 안전 분류체계/예외 사례 묶음은 추가하지 않는다. |
| 메모리와 복원 | 동일 원문/상태로 LIVE와 checkpoint 복원을 비교하고, 공개 대화만 남은 cold 복원은 별도 실행한다. | 실제 원문·질문·정정/요청/중단/보충/안전 이력 보존. 현재 유효 상태와 보관 원문을 구분한다. 정확한 과거 lineage가 없는 cold 복원에서 정밀한 ID/사용량/출처를 발명하지 않는다. 필요한 복구 안내와 일반 질문 가능 여부를 계약대로 구분한다. |
| 입력 크기와 최소 view | 긴 정상 대화와 다중 답변·정정 포함 요청의 실제 SDK kwargs를 측정한다. 같은 원문이 schema enum/slot/리뷰 목록으로 반복되지 않는지도 확인한다. | 정식 기본값48,000 tokens/196,608 bytes에서 시작해 필요하면 첫 canary 전 대표 요청 측정으로 effective 값을 조정하고, 해당 값 안에서 정상 요청이 실제 전달된다. config/runner/SDK가 옛12,000/96 KiB로 회귀하지 않는다. source 32/review 8 같은 새 고정 개수 제한으로 먼저 거절하지 않는다. 용량 초과 때 원문을 몰래 자르거나 다 읽었다고 주장하지 않는다. |
| 실패·중복·취소의 무결성 | 성공 후 동일 requestId 재전송, 같은 ID 다른 payload, Writer/Assessor 오류, timeout/취소를 기존 실행 경계에서 확인한다. | 중복 모델 호출·부분 상태 commit 없음. 실패한 의미 변경은 확정하지 않지만 실제 USER 원문과 시도 ledger는 보존한다. 기술 실패를 NO_CLEAR_DISTORTION/완료/성공 재생으로 바꾸지 않는다. |
| 수집기·blind/full 분리 | 실제 출력의 질문/초안/미판정 안내/중단 안내/안전 응답을 neutral export로 보내고 raw tool call 및 usage와 대조한다. | 같은 공통 blind 형식으로 실제 사용자 표시 내용과 제어 의미가 남는다. 내부 버전/도구 경로/정답을 blind에 노출하지 않는다. 공식 known/봉인 사례와 기대값은 변경하지 않는다. Codex는 점수·우열·등급을 생성하지 않는다. |

## 실행 범위

- 기존 테스트 중 네 영역 완료·모든 source의 SELECT 리뷰·내부 슬롯 개수·문장부호/종결형을 강제하는 검사는 새 계약에 맞게 제거하거나 실제 사용자 기능을 검증하는 검사로 바꾼다. 실패를 무시하는 것이 아니라 폐기한 구조에 대한 요구를 폐기하는 것이다. 출처·철회·기록 무결성 등 여전히 필요한 의미 요구는 유지한다.
- 변환기/schema 단위 확인과 fake provider 통합 확인을 제품의 실모델 성공 건수로 합산하지 않는다. 실제 모델 입력 크기는 실제 SDK kwargs를 기준으로 측정하고 추정 token과 provider usage를 구분한다.
- 첫 유료 호출 전에 실제 적용 source·prompt·schema·canary 입력·기대조건·공통 raw 계약을 잠근다. 12개 제품 요청의 live round 안에서는 코드를 고치거나 실패 문장을 프롬프트에 추가하지 않는다.
- 오프라인 조건과 12개 canary의 필수 기능이 모두 통과하면 기존 승인된 공식 유료 평가와 raw 제출을 이어간다. 문체 관찰만으로 공식 평가를 막지 않는다. 독립 사례의 실패 때문에 아직 실행 가능한 나머지 사례를 곧바로 중단하지 않는다.

이 문서 자체를 작성·검사한 것은 제품 오프라인 테스트나 canary 실행이 아니다.
