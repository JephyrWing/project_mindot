# CBT 기능 범위와 테스트 작성 기준

기준일: 2026-09-09. 이후 작성·잠금하는 실행에 적용한다. 이전 canary/원본 평가 파일/원시 결과를 소급 변경하지 않는다.

이 제품은 기록된 상황과 자동사고를 살펴보는 CBT 대화 기능이다. 사용자가 무엇이든 요청하면 수행하는 범용 LLM이 아니다. 테스트가 새 제품 기능을 만들어 내지 않도록, 기대 행동은 먼저 아래 기존 기능에 연결한다.

| 기존 기능 | 유효한 테스트 | 범위를 벗어난 기대 |
| --- | --- | --- |
| 맥락에 맞는 CBT 질문 | 관찰과 해석, 근거, 다른 관점, 생각의 범위 등을 현재 답변에 맞게 살펴봄 | 원하는 다음 질문·route를 사용자 입으로 정답처럼 지시하고 그 방식만 허용 |
| 현재 CBT 질문의 도움 | 뜻 설명, 답변 방법의 가상 예시 | 일반 보고서·자유 문서·자기소개 등 별도 산출물 작성 |
| 대화 내용 유지 | 정정·부분 철회/복권, 없음·모르겠음·생략 구분, 실제 반복 항의 반영 | 있지도 않았던 질문에 항의하게 하고 반복 방지 기능 실패로 처리 |
| 기존 인지왜곡 검토·사용자 확인 | 유효 자료에 따른 Assessor 후보와 Agent 검토, 기존 확인 화면으로 전달 | “초안을 보여 달라” 한마디로 특정 판정·즉시 완료를 강제 |
| 기존 중단·재개와 기본 위험 대응 | CBT 중단 의사를 존중하고 기존 화면 동작 안내, 명확한 현재 위험 대응 | 제품에 없는 새로운 UI 동작·분류체계·일반 상담 기능을 시험 때문에 추가 |

`outcomeDraft`는 기존 CBT 평가가 끝난 뒤 사용자가 확인·수정할 결과 필드다. 명령형 문서 작성 API가 아니다. 근거가 충분하면 제품의 기존 판단 경로가 이를 제안할 수 있으며, 사용자가 “초안”을 요청해야만 평가할 수 있는 것도 아니다. 반대로 요청 하나로 평가 근거·사용자 확인·DB 완료를 대신할 수 없다.

## 작성할 때 확인할 네 가지

1. 입력과 기대가 기존 기능에 연결되는가. 연결되지 않는 요구는 성공 필수조건에서 제거한다. 범위 밖 요청을 이행하지 않는다는 이유로 기능·도구를 추가하지 않는다.
2. 발화가 자기 입장에서 자연스럽고 실제 이력과 맞는가. “이 답변에 적지 않았다”, 채점용 힌트, 원하는 내부 동작, 존재하지 않는 이전 질문을 사용자 원문에 넣지 않는다. 합성 이력이라는 사실과 실제 연속 대화라는 주장은 구분한다.
3. 기대 필드끼리 모순되지 않는가. 왜곡 없음과 비어 있지 않은 왜곡 코드 목록, 실질 답변과 명시적 없음 라벨, 폐기한 네 영역 완료 의무를 함께 요구하지 않는다. 허용되는 관련 CBT 질문들을 특정 route나 문장 하나로 줄이지 않는다.
4. 결과와 테스트 결함을 구분하는가. 실제 응답 전체를 읽는다. 응답이 있는데 기대 status와 다르다는 것은 기술적 무응답이 아니다. 틀린 기대를 발견하면 TEST_INVALID로 기록하고 원본을 남긴 채 다음 revision에서 고친다. 같은 실행을 소급 PASS로 만들거나 불리한 사례를 몰래 빼지 않는다.

이는 작성자가 자료를 만드는 단계의 검토다. 제품 런타임에 새 검사기·의미 심사 LLM·사용자 시뮬레이터·별도 승인 대기를 추가하지 않는다. 공개 DTO·실제 출처와 정정 효력·원자적 저장·호출 한도 검증은 기능 유지에 필요하다.

## 다음 평가 적용

수정 canary와 공개 known 세트는 이전 원본과 다른 revision으로 잠근다. 원본 파일과 사례 ID, 각 수정 전후·이유·hash를 보존한다. baseline과 candidate에 동일한 개정 입력/기대를 적용하고, 제품 입력에는 채점용 metadata를 보내지 않는다. 과거 점수와 새 점수를 동일 시험의 직접 개선율로 제시하지 않는다.

공식 수집 목표 184사례×2버전=368결과는 유지한다. 제외로 분모를 줄이거나 수정되지 않은 옛 expected를 현재 정답으로 섞지 않는다. 공개 단일160·장기10에 대한 수정은 개정 manifest가 명시한다. 봉인14의 키·평문은 이 작업에서 열지 않는다. 따라서 봉인 사례의 품질까지 전수 검토했다고 주장하지 않는다.

봉인 공개 뒤에도 적용할 범위 판정 원칙은 지금 이 문서로 고정한다. 이후 발견되는 테스트 오류는 별도 결함으로 기록하고 양쪽에 같은 기준으로 해석한다. 실행 중 입력/기대값/분모를 교체하거나 제품을 그 사례에 맞춰 수정하지 않는다. 잘못된 기대와의 기존 일치율을 제품 성공률로 이름 바꾸지 않는다.
